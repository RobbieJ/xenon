# Research: full-duplex AirPods-to-AirPods voice link on iOS 26/27 (audio capture and session)

*Research date: 10 September 2026. Sources are linked inline. Confidence levels are the researcher's own.*

## 1. AVAudioSession configuration and the AirPods microphone path

**What the modes do.** Apple's documentation for `.voiceChat` states that setting it "optimizes the device's tonal equalization for voice and reduces the set of allowed audio routes to only those suitable for voice chat" and "causes the system to automatically apply the `allowBluetoothHFP` category option". `.videoChat` does the same but also applies `.defaultToSpeaker`. Critically, if you use a chat mode *without* AUVoiceIO / `setVoiceProcessingEnabled(true)`, "the system reduces the processing it applies... it doesn't apply voice-specific processing, like echo cancellation and automatic gain correction, and disables dynamic processing on input and output, which results in a lower playback level" ([voiceChat](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat), [videoChat](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/videochat)). `.allowBluetooth` is renamed `.allowBluetoothHFP` in the iOS 26 SDK ([dotnet/macios AVFAudio iOS 26 diff](https://github.com/dotnet/macios/wiki/AVFAudio-iOS-xcode26.0-b1)); it is valid only with `.record`/`.playAndRecord` and is orthogonal to `.allowBluetoothA2DP` (output-only, no mic) ([allowBluetoothHFP](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetoothhfp)).

**Profile/codec on the AirPods mic path.** Any session that takes AirPods *input* puts them into HFP (SCO, 64 kbit/s fixed bidirectional). Standard HFP codecs are CVSD (8 kHz) and mSBC (16 kHz); iOS logs show "Setting SCO audio codec to mSBC at sample rate of 16000" for generic headsets ([HN thread](https://news.ycombinator.com/item?id=24774912)). For AirPods 3 / AirPods Pro and later, Apple added **AAC-ELD at 24 kHz mono, bidirectional** over the same SCO link, discovered by Marco Pfeiffer and confirmed by Apple's AirPods 3 marketing ("superior speech codec... full HD voice") ([AppleInsider](https://appleinsider.com/articles/22/02/01/apple-quietly-improved-call-audio-quality-on-airpods-pro-airpods-3), [iDropNews](https://www.idropnews.com/news/apple-snuck-in-some-big-improvements-to-call-quality-in-airpods-3-and-airpods-pro/178979/)). Corroboration from developer reports: older AirPods reported `sampleRate == 16000` in `playAndRecord` ([forum 665814](https://developer.apple.com/forums/thread/665814), 2020), whereas current AirPods report **24000 Hz** for the HFP route (a macOS Sequoia thread shows the correct AirPods stream format is 24 kHz, and a beta tester noted Voice Memos files went "from 24 kHz... to 48 kHz" after the iOS 26 firmware) ([forum 770232](https://developer.apple.com/forums/thread/770232), [MacStories](https://www.macstories.net/news/testing-airpods-4s-beta-update-and-improved-recording-quality-for-voice-notes/)). **So expect the third-party HFP path on AirPods Pro 2/3 and AirPods 4 on iOS 17-27 to be AAC-ELD, 24 kHz mono, ~12 kHz audio bandwidth, with mSBC 16 kHz as the fallback.** Confidence: high that it is 24 kHz on current AirPods; medium that it is specifically AAC-ELD on every session type (no Apple document states the codec).

**Buffer and sample-rate preferences.** Set `preferredSampleRate` to 24000 (or 48000 and let the system convert) and `preferredIOBufferDuration` to 0.005-0.01 s; the hardware will report whatever it wants. A WebRTC log with AirPods Pro showed `IOBufferDuration 0.020`, `outputLatency 0.0215`, `inputLatency 0.005` ([forum search summary](https://developer.apple.com/forums/tags/avaudiosession/?page=4&sortBy=newest)). Note the WebRTC log's 21.5 ms output latency is the *HFP* figure; A2DP reports ~160 ms.

## 2. iOS 26 "studio-quality" / high-quality Bluetooth recording

Apple's newsroom: available for AirPods 4, AirPods 4 (ANC) and AirPods Pro 2 (and Pro 3) via firmware; uses "the H2 chip, beamforming microphones, and computational audio"; supports Camera, Voice Memos, dictation, "video conferencing apps like Webex, and compatible third-party camera apps" ([Apple Newsroom](https://www.apple.com/newsroom/2025/06/airpods-now-more-versatile-with-studio-quality-audio-recording-and-camera-remote/)). WWDC25 session 251 describes it as "a new high quality, high sample rate, bluetooth option for apps that feature audio capture... a more reliable bluetooth link that is designed specifically for AirPods high quality recording", enabled with `AVAudioSession.CategoryOptions.bluetoothHighQualityRecording` (or `AVCaptureSession.configuresApplicationAudioSessionForBluetoothHighQualityRecording`), with `allowBluetoothHFP` as fallback ([WWDC25 251](https://developer.apple.com/videos/play/wwdc2025/251/)). Apple never states the codec; observed output is 48 kHz files (MacStories, above). Third-party apps are **not** given it automatically; you must opt in.

**The deal-breakers for this app, from the API doc** ([bluetoothHighQualityRecording](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/bluetoothhighqualityrecording)): "You can request high-quality recording only when using the `default` audio session mode"; it "may increase input latency... not recommended for real-time communication"; and "Bluetooth high-quality recording isn't currently supported in the European Union" (UK is outside the EU, but check the region gate on device). Capability is queryable via `AVAudioSessionPortDescription.bluetoothMicrophoneExtension.highQualityRecording.isSupported/isEnabled` (iOS 26, also exposes `farFieldCapture`) ([AVAudioSessionPortExtensionBluetoothMicrophone](https://developer.apple.com/documentation/avfaudio/avaudiosessionportextensionbluetoothmicrophone), [AVAudioSessionCapability](https://developer.apple.com/documentation/avfaudio/avaudiosessioncapability)). Whether it can be combined with voice processing (VPIO) is undocumented and, given the `.default`-mode requirement, probably not. **iOS 27**: nothing changed here that I could find (see section 9). Confidence: high.

## 3. Voice Isolation microphone mode

`AVCaptureDevice.preferredMicrophoneMode` is a **read-only** class property ("the microphone mode that the user selects in Control Center"; observe with KVO); `activeMicrophoneMode` is what is actually running ([preferredMicrophoneMode](https://developer.apple.com/documentation/avfoundation/avcapturedevice/preferredmicrophonemode)). An app cannot set it; it can only call `AVCaptureDevice.showSystemUserInterface(.microphoneModes)`. Voice Isolation requires the voice-processing pipeline (AEC on, so AGC on) and "has been tested to work with both the iPhone Built-In microphone as well as Bluetooth devices like AirPods Pro" ([PhenixRTS](https://phenixrts.com/docs/knowledge-base/how-to/ios-audio-pipelines/)). Apple support says third-party (FaceTime-style) apps get mic modes from iOS 15, phone calls from 16.4, *recording* apps only from iOS 26, and iOS 18 added an "Automatic" mode ([Apple 101993](https://support.apple.com/en-us/101993)). The processing runs on the iPhone (an ML mask; the same engine as `AUSoundIsolation`, iOS 16+, ([kAudioUnitSubType_AUSoundIsolation](https://developer.apple.com/documentation/audiotoolbox/kaudiounitsubtype_ausoundisolation))), so it applies to the decoded 24 kHz AirPods stream, not inside the earbuds. iOS 26's `AVInputPickerInteraction` (AVKit) shows the picker with mic-mode selection in-app ([WWDC25 251](https://developer.apple.com/videos/play/wwdc2025/251/)). No published latency figure; it is frame-based and appears to add tens of ms at most (unmeasured). Confidence: high on API constraints, low on latency.

## 4. AVAudioEngine voice processing (AUVoiceIO)

`inputNode.setVoiceProcessingEnabled(true)` enables VPIO on both IO nodes (mono output only), and implicitly sets `.voiceChat` if no chat mode was set. `isVoiceProcessingAGCEnabled` (iOS 13+) is "enabled by default" and controls AGC on the uplink ([isVoiceProcessingAGCEnabled](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/isvoiceprocessingagcenabled)). `voiceProcessingOtherAudioDuckingConfiguration` (iOS 17+) sets `enableAdvancedDucking` and `duckingLevel` (`.default`, `.min`, `.mid`, `.max`) for *non-voice* audio; default is advanced ducking off ([doc](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/voiceprocessingotheraudioduckingconfiguration)). Developers hit an iOS 17 regression where VPIO lowered playback volume ([forum 739160](https://developer.apple.com/forums/thread/739160)). A 2026 field report, citing an Apple DTS engineer, says VPIO "subtracts the output signal from the input signal" with no tunable parameters; the residual echo window is 200-500 ms; Bluetooth routes "increase latency unpredictably"; and VPIO only works properly in `.voiceChat`, with the playback graph attached before enabling it ([barock.dev](https://barock.dev/2026/04/22/why-your-ios-voice-agent-still-hears-itself)). Also useful: `setPrefersEchoCancelledInput` (iOS 18.2) is only for `.default` mode with the *built-in* mic/speaker and switches off on headset routes, so not relevant here ([doc](https://developer.apple.com/documentation/avfaudio/avaudiosession/setprefersechocancelledinput(_:))). Bottom line: with AirPods there is no acoustic echo path (sealed ear tips), so VPIO's AEC is nearly irrelevant, but it is the only way to get Apple's noise suppression, AGC and the Voice Isolation mic mode. Confidence: high.

## 5. AirPods behaviours that will interfere (none controllable by apps)

None of these have a public API; the only lever is user guidance. Settings per Apple ([listening-mode settings](https://support.apple.com/guide/airpods/adjust-listening-mode-settings-dev6d977ff21/web), [Adaptive Audio](https://support.apple.com/en-us/104979)):

- **Conversation Awareness** (AirPods 4 ANC, Pro 2/3, Max 2): when the wearer speaks, lowers media volume, reduces noise and "enhances voices in front of you"; it triggers on the speech-detecting accelerometer, so in your app it will duck the far person every time the near person talks and open Transparency in a loud room. Tell users to turn it off (Settings > AirPods > Conversation Awareness, or Control Center long-press volume).
- **Adaptive Audio**: blends ANC/Transparency by ambient level; iOS 27 exposes a simplified slider ([iphon.fr](https://www.iphon.fr/post/airpods-pro-apple-surprise-ios-27)). Tell users to force Noise Cancellation.
- **Personalized Volume** and **Loud Sound Reduction**: adjust playback level automatically; disable for a stable link.
- **Conversation Boost** (Accessibility > Audio/Visual > Headphone Accommodations > Transparency Mode): beamforms *ambient* voices in Transparency; measured to add 2 dB SNR alone, 3.5 dB with ambient noise reduction ([Hearing Review / NAL](https://hearingreview.com/hearing-products/hearing-aids/otc/evaluating-apple-airpods-pro-2-hearing-aid-software-acoustic-measurements-and-insights)). Irrelevant in ANC mode; off.
- **Automatic Ear Detection**: removing one bud pauses/reroutes audio to the phone; your app must observe `AVAudioSession.routeChangeNotification` and re-select the AirPods input.
- **Automatic Switching** ("Connect to This iPhone: Automatically"): a Mac/iPad can steal the AirPods mid-call; recommend "When Last Connected to This iPhone".

Detection: you can only detect the *route* (port type `.bluetoothHFP`, port name, `bluetoothMicrophoneExtension` capabilities) and a `productID`-style name; feature toggles are invisible. Confidence: high.

## 6. Does ANC stay on in HFP call mode?

Yes. Apple's spec sheets list ANC/Transparency/Adaptive as listening modes independent of profile, and Live Translation explicitly relies on it: "Active Noise Cancellation (ANC) lowers the volume of the person speaking so it's easier to focus on the translation" ([Apple Newsroom, Sept 2025](https://www.apple.com/newsroom/2025/09/new-apple-intelligence-features-are-available-today/)). Apple's ANC page contains no call-mode caveat ([Apple 108918](https://support.apple.com/en-us/108918)). Community reports of ANC "feeling weaker" on calls are anecdotal and mostly reflect sidetone (own-voice feed-through) that Apple enables on calls; there is no documented degradation. The real quality loss in call mode is the *downlink* (24 kHz mono AAC-ELD vs 44.1/48 kHz AAC over A2DP), which is fine for speech. Confidence: medium-high.

## 7. Latency numbers

- **A2DP (media) on AirPods**: `outputLatency` reports ~160-163 ms; measured end-to-end 215-220 ms right after connection, settling to 155-160 ms after 20-30 min ([forum 679274](https://developer.apple.com/forums/thread/679274), [Apple Community](https://discussions.apple.com/thread/256097737)).
- **HFP on AirPods**: `outputLatency` reports ~9-21.5 ms, `inputLatency` ~5 ms, but one test measured only ~30 ms real improvement over A2DP ([Apple Community](https://discussions.apple.com/thread/256097737)); the WebRTC log above suggests ~20 ms buffers. Realistic budget: 40-80 ms each way through the Bluetooth stack, i.e. capture-side ~40-60 ms and playback-side ~40-60 ms. **This is the single biggest open measurement.**
- **Reference points**: Live Listen (iPhone mic to AirPods, Apple's own pipeline) is quoted at ~150 ms on iPhone 13 ([Apple Community](https://discussions.apple.com/thread/254988449)); the AirPods Pro 2 hearing-aid mode's processing delay was not published by NAL ([Hearing Review](https://hearingreview.com/hearing-products/hearing-aids/otc/evaluating-apple-airpods-pro-2-hearing-aid-software-acoustic-measurements-and-insights)) but is in-bud and therefore single-digit ms.
- **Target**: ITU-T G.114: 0-150 ms one-way "essentially transparent"; 150-400 ms acceptable with increasing degradation; >400 ms unacceptable ([ITU-T G.114](https://www.itu.int/rec/dologin_pub.asp?lang=e&id=T-REC-G.114-200305-I!!PDF-E&type=items)). Two Bluetooth hops (~50 + ~50 ms) + 20 ms frame + NS (10-40 ms) + Wi-Fi Aware (<10 ms) lands around 150-200 ms mouth-to-ear: usable, not "transparent". Confidence: medium (few rigorous measurements exist).

## 8. Apple's own related features

- **Live Listen** (iPhone mic to AirPods, ~150 ms): no API. **Conversation Boost / Hearing Aid** (in-bud DSP, Pro 2/3): no API; hearing-aid gain is NAL-NL2 prescriptive ([Apple 120992](https://support.apple.com/en-us/120992), Hearing Review above). **Live Translation** (iOS 26; AirPods 4 ANC, Pro 2/3, Max 2; iPhone 15 Pro+): fully on-device; started by squeezing both stems, Siri, Action button, or the Translate app "Live" tab; "When both people are wearing supported AirPods, each participant hears a translation... in the language of their choice"; the iPhone shows a live transcript and can play audio through its speaker; in noise, "use the microphone on your iPhone to improve the translation input quality" ([Apple 123185](https://support.apple.com/en-us/123185), [in-person guide](https://support.apple.com/guide/airpods/translate-in-person-conversations-dev9c215ca94/web)). Nothing is exposed to third parties (the Translation framework is text-only). **Design patterns worth copying**: the double-stem-squeeze "start session" gesture (not available to apps, but a big on-screen Start button plus Action-button App Intent approximates it), ANC-on as the default listening state, a live transcript on screen as a fallback channel, and offering the iPhone mic as an alternative capture source in extreme noise.
- **iOS 27 LiveCommunicationKit** (WWDC26 session 226) replaces CXProvider: Lock Screen/Dynamic Island call UI, and "if the person switches to AirPods... your app gets a route change notification and updates its capture pipeline" ([WWDC26 226](https://developer.apple.com/videos/play/wwdc2026/226/)). Using it (or CallKit) makes the session a system "call", which is what unlocks the call-grade mic modes and keeps the session alive in background.

## 9. WWDC 2026 / iOS 27: confirmed vs rumoured

**Confirmed**: custom AirPods EQ (highs/mids/lows) in iOS 27 ([AppleInsider](https://appleinsider.com/articles/26/06/08/airpods-finally-gain-custom-eq-feature-in-ios-26), [SoundGuys](https://www.soundguys.com/apple-airpods-custom-eq-158520/)); simplified Adaptive Audio slider and reorganised AirPods settings ([iphon.fr](https://www.iphon.fr/post/airpods-pro-apple-surprise-ios-27), [MacRumors](https://www.macrumors.com/2026/05/24/new-ios-27-details-ahead-of-wwdc/)); LiveCommunicationKit (session 226); Bluetooth Channel Sounding for accessories (session 369); a new `AudioAccessoryKit` for third-party spatial-audio headphone metadata (iOS 27 release notes). The iOS 27 RC release notes contain **no** AVFAudio/AVAudioSession/Core Audio entries ([iOS 27 release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes)), and the WWDC26 catalogue has no AVAudioSession/AirPods audio session ([WWDC26 videos](https://developer.apple.com/videos/wwdc2026/)). **Not announced / rumour only**: LE Audio / LC3 / Auracast on iPhone or AirPods (AirPods Pro 3 spec sheet lists only "Bluetooth 5.3", H2, dual beamforming mics, inward mic, speech-detecting accelerometer ([Apple 125135](https://support.apple.com/en-us/125135)); Apple still has not shipped Auracast ([Apple Community](https://discussions.apple.com/thread/255961178))); any AirPods latency improvement; any third-party access to Live Translation or hearing features. Plan on iOS 26 APIs; iOS 27 adds nothing you need. Confidence: high on the absence in release notes; medium that no AirPods audio-stack change shipped silently.

## 10. Third-party on-device noise suppression

| Option | Frame / added latency | Compute | Notes |
|---|---|---|---|
| **RNNoise** (BSD) | 10 ms frames @48 kHz, ~10 ms | 60x real-time on x86, 7x on Raspberry Pi 3; 85 kB weights ([jmvalin](https://jmvalin.ca/demo/rnnoise/)) | Negligible on A-series; resample 24k to 48k. Weakest on babble. |
| **DeepFilterNet3** (MIT/Apache) | 20 ms window, 10 ms hop, 2-frame look-ahead: ~40 ms | RTF 0.19 laptop thread, 0.42 Raspberry Pi 4; ~2 M params ([Forasoft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-noise-suppression-krisp-rnnoise-deepfilternet), [GitHub](https://github.com/Rikorose/DeepFilterNet)) | Best quality on crowd/restaurant noise; needs an ONNX/Core ML port (Rust/tract crate builds for iOS). |
| **Krisp SDK** (commercial) | 10 ms frames, ~25 ms (15 ms "lite"); 8/16/32 kHz native ([Krisp docs](https://sdk-docs.krisp.ai/docs/noisecancellation)) | "Small" models 7x faster than "Big"; iOS SDK 9.9 gave 10-50% CPU cut | Best babble/other-voice rejection; licensed via sales. |
| **WebRTC APM** (NS + AGC2 + AEC3) | 10 ms frames, ~0-10 ms | 4-13 µs per 10 ms frame on Apple M4 ([Sonora benchmarks](https://github.com/dignifiedquire/sonora/blob/main/BENCHMARKS.md)) | Classical spectral NS; cheap, modest on babble. |
| **Apple** VPIO NS + Voice Isolation (`AUSoundIsolation`) | undocumented, likely 10-30 ms | Neural Engine / CPU | Free, tuned for iPhone; Voice Isolation is user-toggled only. |

Confidence: high on figures; medium on iOS ports of DeepFilterNet.

## Recommended pipeline

**Session**: `.playAndRecord`, mode `.voiceChat`, options `[.allowBluetoothHFP]` only (no A2DP, no defaultToSpeaker); `preferredSampleRate` 24000, `preferredIOBufferDuration` 0.01; wrap the call in LiveCommunicationKit/CallKit so the system treats it as a call (mic modes appear in Control Center, background audio survives). Do **not** use `bluetoothHighQualityRecording` (requires `.default` mode, adds latency, region-gated).

**Capture**: `AVAudioEngine.inputNode` with `setVoiceProcessingEnabled(true)` (attach the playback graph first), AGC on, `voiceProcessingOtherAudioDuckingConfiguration = (advanced: false, .default)`; prompt users once via `showSystemUserInterface(.microphoneModes)` to pick Voice Isolation. Tap at 24 kHz mono; stack a second-stage NS (RNNoise for v1; DeepFilterNet3 or Krisp behind a setting for restaurants), then a VAD-driven noise gate/comfort-noise so the far side is not fed the aircraft rumble.

**Encode/transport**: Opus (libopus, 16-24 kHz, 20 ms frames, 24-32 kbit/s, FEC on, DTX on) over UDP via Wi-Fi Aware (`WAPerformanceMode.realtime`, iOS 26+, same mode both sides ([WAPerformanceMode](https://developer.apple.com/documentation/wifiaware/waperformancemode))), with Network.framework `includePeerToPeer` + `.interactiveVoice` as fallback on older hardware (AWDL's undocumented realtime mode cannot be forced ([forum 819926](https://origin-devforums.apple.com/forums/thread/819926))). Jitter buffer 40-60 ms adaptive.

**Playback**: decode to a mono `AVAudioPlayerNode`/source node into the voice-processing output node at hardware rate; keep the wearer in ANC (Adaptive Audio and Conversation Awareness off); optionally mix a little of the local mic as sidetone since ANC plus occlusion makes people shout.

**Onboarding checklist for users**: Noise Cancellation on; Conversation Awareness, Adaptive Audio, Personalized Volume, Loud Sound Reduction off; Automatic Switching set to "when last connected"; Voice Isolation selected in Control Center.

## Open questions needing on-device measurement

1. True mouth-to-ear latency across two AirPods HFP hops (Pro 2 vs Pro 3 vs AirPods 4) with VPIO on/off, including the "warm-up" drift seen on A2DP.
2. Whether the third-party `.voiceChat` route on iOS 26/27 actually negotiates AAC-ELD 24 kHz on all three models, or falls back to mSBC when another device is paired.
3. Added latency and CPU of Voice Isolation on the AirPods route, and how well it rejects a nearby talker (the other participant sitting across the table) versus DeepFilterNet3/Krisp.
4. Whether `bluetoothHighQualityRecording` can be activated alongside voice processing at all, and its measured input latency.
5. Behaviour when Conversation Awareness is left on: does it duck app audio or only Music-type media?
6. Wi-Fi Aware realtime-mode packet latency/jitter on an aircraft with dozens of other 2.4/5 GHz devices, and Bluetooth/Wi-Fi coexistence effects on the SCO link.
7. ANC sidetone behaviour: does iOS inject own-voice sidetone during a third-party VoIP session, and can it be suppressed?
