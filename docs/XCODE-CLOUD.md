# Building with Xcode Cloud

Xcode Cloud is Apple's hosted build and test service, part of App Store Connect. It is the right
CI for this project for one reason above all: it always carries the current Xcode, so it can build
the iOS 27 target now, while GitHub's macOS runners are still on Xcode 26.6. It also handles code
signing and can push every green build to TestFlight.

## What you get

- Builds against the newest Xcode and iOS SDK, including release candidates.
- Automatic cloud signing. No certificates or profiles to manage.
- TestFlight upload on every build of a chosen branch, with internal testers notified.
- 25 compute hours a month included with the Apple Developer Programme; more can be bought.
- Works with a private GitHub repository.

## What it cannot do

- No physical devices. Tests run on simulators, and this app's audio and radio code needs real
  iPhones. Treat Xcode Cloud as "does it compile, do the unit tests pass, ship it to TestFlight",
  and do the real testing on two phones from TestFlight.
- It needs an Xcode project or workspace committed in the repository. Ours is generated from
  `project.yml`, so the generated `Sotto.xcodeproj` is committed as well and regenerated by
  `ci_scripts/ci_post_clone.sh` on every build so it can never drift.

## One-time setup (about ten minutes, on a Mac with Xcode 27)

1. **App Store Connect record.** In App Store Connect, create the app with bundle identifier
   `uk.org.shadowtech.sotto` (change it in `project.yml` first if you want another). Xcode Cloud
   can create this for you during step 3, but it is clearer to do it first.
2. **Team in the project.** Set `DEVELOPMENT_TEAM` in `project.yml` to your team ID, run
   `xcodegen generate`, and commit both.
3. **Create the workflow.** Open `Sotto.xcodeproj` in Xcode, then Product › Xcode Cloud › Create
   Workflow. Xcode walks through: choose the `Sotto` product, review the default workflow, grant
   Xcode Cloud access to the GitHub repository (it installs the Xcode Cloud GitHub App; pick just
   this repository), and confirm. Xcode Cloud then runs a first build.
4. **Edit the default workflow** (App Store Connect › the app › Xcode Cloud › Workflows, or from
   Xcode's Cloud tab):
   - Start conditions: every push to `master`, plus pull requests.
   - Environment: newest Xcode release (or the release candidate while iOS 27 is new).
   - Actions: Build for iOS on the `Sotto` scheme, and Archive with TestFlight (internal testing)
     for `master` only.
   - Post-actions: TestFlight internal group, so both test phones get the build automatically.
5. **Add testers.** App Store Connect › TestFlight › Internal Testing: add the Apple IDs of the
   two phones' owners. They install TestFlight, accept the invitation, and every green `master`
   build appears on both phones.

## What the repository already provides

- `ci_scripts/ci_post_clone.sh`: installs XcodeGen, regenerates the project, and runs the
  `SottoKit` package tests. Xcode Cloud runs it automatically because of its location and name.
- `Sotto.xcodeproj`: committed so Xcode Cloud can find the scheme when the workflow is created.
- The `Sotto` scheme is shared (XcodeGen does this by default).

## Relationship to the GitHub Actions workflow

Keep both. GitHub Actions runs the package tests on Linux and macOS quickly and for free on every
pull request. Xcode Cloud is the one that builds the real app, signs it and delivers it to phones.
When GitHub's runners gain Xcode 27 the advisory iOS job there becomes a second opinion, nothing more.

## Costs to watch

A full archive plus TestFlight upload for this app should take a few minutes on Xcode Cloud. At a
handful of builds a day that is well inside the 25 free hours. Add tests on simulators sparingly,
they are the slow part.
